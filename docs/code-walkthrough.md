# Code walkthrough

1. **Start with the wrapper and POM.** The wrapper downloads a checksum-pinned Maven 3.10.0. `clean` removes build output; `validate` enforces Java/Maven and live opt-in; `test-compile` compiles test-focused code; Surefire executes the explicit suite in `test`; `verify` checks formatting. An empty application JAR is not packaged. There is no deploy/release lifecycle customization.
2. **Trace configuration.** `TestConfig.from` reads explicit properties over defaults, checks suite/lane agreement, rejects unsupported browsers and strictly parses booleans/timeouts. Live requires profile marker, opt-in and exact base origin. Validation occurs before browser creation. The listener also validates result-path agreement at suite start.
3. **Follow TestNG ownership.** `BaseTest.setUp`, annotated `@BeforeMethod(alwaysRun = true)`, creates one driver. DataProvider rows are separate invocations, so each gets this lifecycle. `@AfterMethod(alwaysRun = true)` quits and clears it even after failure. A cleanup exception is suppressed onto an existing throwable; otherwise it is thrown as a failing configuration.
4. **Inspect DriverFactory.** Options select headless mode and a fixed window, reduce startup background traffic and leave certificate/security checks enabled. `EAGER` waits for DOM readiness; page objects retain explicit waits for meaningful application state, without depending on every page resource completing. `new ChromeDriver` uses Selenium Manager because no driver path is supplied. Connection, read, page and script budgets are bounded; implicit waits are zero. Failed post-creation initialization attempts cleanup before rethrowing.
5. **Read pages from a test.** ProductCatalogueTest creates ProductsPage with its driver and configuration. ProductsPage returns scoped ProductCard components; a card follows its native details link. ProductDetailsPage exposes fields and one cart action. CartPage only reads rows. No page creates a driver or makes business assertions.
6. **Inspect waits.** Search waits for the old heading to become stale and the replacement document heading to be visible. Details wait for their information block. Cart waits for confirmation and the cart table. These are observable conditions, not fixed sleeps. No generic BasePage is needed for a few clear waits.
7. **Find assertions.** Tests compare all displayed search results, cross-page identity and exact decimal prices. Cart total is calculated in the test with BigDecimal. The two-row DataProvider deliberately covers only verified unmatched and empty-input behavior.
8. **Inspect diagnostics.** Allure's TestNG service listener records native test/fixture status and stack traces. Runtime `Allure.step` calls describe business actions. FailureEvidenceListener uses only DriverProvider's Optional driver access. It captures before teardown, caps PNG output and leaves successful screenshots inside Allure. Its optional fallback runs only on attachment failure. Reporting exceptions are caught separately and never replace the primary TestNG throwable.
9. **Read deterministic tests.** Configuration/options tests need no browser. Small driver doubles check lifecycle and evidence failure handling. LocalChromeTest invokes the real factory twice and proves clean browser state against the same loopback origin. The fixture is a button and status text, not a sample business application.
10. **Read both workflows.** Deterministic validation runs for pull requests and main pushes, without secrets. Manual live validation requires a dispatch checkbox and fixed CLI arguments, and first passes deterministic validation. Uploads use `always()` and separate artifacts for each lane. Java caching and action SHA pins support reproducibility; runner Chrome and Java patch versions still evolve.

Chrome-only sequential execution deliberately keeps ownership, diagnostics and traffic easy to explain. Parallel execution, multiple browsers, Grid, retries, dashboards and hosted reports would introduce new responsibilities and are deferred. The Windows socket-directory accommodation is described in running-tests.md; it does not alter application behavior or global settings.
